# Mini Order Service：渐进式项目约定

## 使用场景与实现边界

为小型商家管理商品，为用户创建、查询和取消订单。优先训练 HTTP、SQL、事务与正确性；第一阶段采用单体服务与单个 MySQL 实例。

当前先在已有 `examples/axum_1` 里演进，避免重建 Hello World。达到 V1 时由学习者选择迁移到 `projects/mini_order_service`；若迁移，需要自行将路径加入 Cargo workspace members。规划文档不自动生成 crate、迁移代码或完整服务实现。

V2 先支持单商品订单；多商品、真实支付、跨库事务、完整商城、微服务拆分均为后续可选。需要展示支付状态时使用明确标注的模拟事件。

## 数据与业务不变量

商品：`id`、`name`、`price_cents`、`stock`、`active`、时间字段。价格使用固定货币的整数最小单位，先不用浮点金额；考虑乘法溢出与最大订单金额。

订单：`id`、`user_id`、商品 ID、数量、单价快照、总额、状态、时间。V2 用户身份来自仅限本地测试的固定上下文，不信任请求体 user_id；V3 改为认证提取。订单记录不依赖商品当前价格。已有关联订单的商品采用下架而不是随意硬删除。

不变量与证明义务：

1. 数量是有上限的正整数；库存非负；价格由服务端读取。
2. 创建成功的订单与扣减处于同一事务；事务失败不留下半次创建。
3. 初始库存为 N、无补货/取消时，成功购买数量之和不超过 N。一次单进程压力测试不是完整证明，需要解释 SQL 更新/锁/约束的作用。
4. 同一用户和幂等键的相同请求只产生一个订单；不同请求内容复用同键返回冲突。将范围、请求摘要、结果与业务写入协调处理；不能靠进程内 HashMap 解决多实例竞争。
5. 客户端超时不等于订单创建失败；重试必须能定位同一个结果。
6. `created → cancelled`、`created → completed` 是允许的迁移；终态不回到 created。完成事件仅为模拟；取消回补最多一次，必须与状态迁移原子协调。
7. 用户只能访问自己的订单；商品写操作仅管理员。V2 尚未认证的接口只用于本地练习。
8. 商品缓存允许明确的短暂陈旧；下单的价格/库存依据来自数据库。文档不能声称 Cache Aside 自动保证强一致。
9. 通知任务与订单写入同事务产生事件，可能重复投递；消费者副作用必须能去重。

## 第一版 API 约定

| 接口 | 输入/输出重点 | 约定 |
|---|---|---|
| `GET /healthz` | 简单存活响应 | 200；后续另设 readiness 检查依赖，避免混淆 |
| `GET /products` | 商品列表，V1 加分页 | 200；空列表为数组，不是 404 |
| `GET /products/:id` | 商品详情 | 200 或 404；路径 ID 格式错误 400 |
| `POST /products` | name、price_cents、stock | 201；错误输入 400，V3 要管理员 |
| `PUT /products/:id` | 完整商品属性 | 200、400、404；订单上线后 stock 改由受控库存路径管理，不任意覆盖 |
| `DELETE /products/:id` | V0 可删除，V1/V2 采用下架 | 204 或 404；保留订单引用 |
| `POST /orders` | product_id、quantity；Idempotency-Key | 201；相同请求重试返回原结果并文档化；不足库存/同键异载荷 409 |
| `GET /orders/:id` | 订单快照与状态 | 200；无身份 401，按统一策略处理无权限与不存在 |
| `POST /orders/:id/cancel` | 条件状态迁移 | 200；重复取消返回同一终态，不重复回补；已完成返回 409 |
| `POST /sessions` | 第 6 周添加登录 | 验证凭据、会话过期；使用成熟密码哈希库，不自制算法 |

表中路径参数使用现有 Axum 0.7 语法；项目选 0.8 时统一迁移。请求 schema、响应示例、幂等返回码和权限策略由学习者在实现前写入项目 API 文档，以上是起始约定。

业务错误 envelope：`code`、`message`，第 2 周起加入 `request_id`。服务端记录数据库等详细错误，外部响应避免泄露 SQL、凭据与内部堆栈。401/403、非法 JSON 与 500 的边界要明确。

## 必做实验

### E1 请求边界

测试未知路由、错误方法、非数字 ID、非法 JSON、缺字段、负数、空商品名、过大请求体。记录实际状态与响应类型，解释框架拒绝发生在哪一层。

### E2 持久化与事务

重启应用后数据仍在；全新测试数据库能迁移。注入订单写入失败，核对订单数和库存均符合回滚预期。每个测试使用隔离的库/数据，不通过重置开发数据获得稳定结果。

### E3 并发与幂等

库存 10，100 个同时开始的单数量购买请求，成功量不超过 10。记录成功、冲突、其他失败；理想健康环境下最终成功量为 10，出现其他失败必须解释。对同幂等键并发请求，验证只有一个订单。加入两个服务实例连接同数据库，排除只靠内存锁实现的正确性。

### E4 缓存

比较冷/热缓存；数据库更新与失效之间插入失败；停止 Redis；对热点同时请求。写清降级行为和可能陈旧窗口，不用“最终一致”四个字代替恢复机制。

### E5 可靠任务

在事务提交后发布前、消费者副作用后确认前注入退出/失败；重启后事件能继续处理，重复处理不重复产生业务副作用。超出重试上限进入明确失败状态并可检查/重放。Outbox 的同事务写入和重复投递问题可参考 [AWS 说明](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。

### E6 部署与性能

依据 README 在隔离环境启动并迁移。固定机器、软件版本、payload、读写比例、连接数/并发、预热和持续时长；测量吞吐、p50/p95/p99、错误率、CPU/内存、连接池等待与任务积压。负载机与服务同机时注明影响。先基线、再证据、再优化，吞吐数字不预设。

## 工程边界

本项目是 Rust → Go 路线的第一阶段。Rust 核心完成标准和可延期扩展见 [阶段切换](go_project_phase.md)；V4/V5 描述演进方向，不意味着每个高级功能都必须做完才允许进入 Go。

- Handler 负责 HTTP 转换；业务函数维护不变量；存储函数管理 SQL。只有复杂度出现时才提取，不先搭大型分层框架。
- 依赖按需求添加并解释：Serde 处理 JSON，SQLx 连接 MySQL，Redis 客户端处理缓存，tracing 提供结构化诊断。不要为短练习加入完整微服务框架。
- 测试使用者自己写；学习者先描述最可能失败的场景，再决定断言。
- 示例命令随项目 README 维护；针对当前 crate 用 `cargo check -p axum_1`、`cargo test -p axum_1`。迁移后使用实际包名。
- Git 提交按学习里程碑，不提交 target、数据库数据目录、真实配置密钥与日志；执行提交/推送需用户指示。
