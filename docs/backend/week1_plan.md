# Mini Order Service 第一周：内存商品服务

规划日期：2026-11-05。任务编号沿用 W01-D1～D7，按实际学习进度推进，不绑定自然周。当前检查到 `examples/axum_1` 仍为 Hello World；下面所有新功能都待学习者实现与验收。

## 本周成果与边界

目标：独立完成 Mini Order Service 的 V0——内存商品管理 HTTP 服务，能解释一条请求如何读取或修改共享状态，并验证正常与失败路径。

商品是订单的前置模型：后续下单需要找到商品、读取服务端价格、检查并扣减库存。因此本周先把 HTTP 接口与数据访问做扎实，第二周接 MySQL，之后再加入订单事务。

本周实现健康检查、商品 CRUD、输入验证、错误响应和路由测试；数据库、Redis、登录、下单、防超卖和消息队列安排在后续阶段。内存集合的锁只保护当前进程，不代表已经实现数据库层的防超卖。

继续在现有 `examples/axum_1` 演进，暂不迁移目录。当前锁文件为 Axum 0.7.9，按对应版本查阅 API，不因新规划升级依赖。

完整知识讲解、增量任务、命令、常见错误与提示继续使用同一份 [主题材料](study_materials/http_axum_in_memory_products.md)。本文仅细化周任务，不另建七份每日教材。

## Day 1：从 TCP 服务走到 HTTP API（W01-D1）

- 理论（H/A）：HTTP 请求/响应结构；Router 与 Handler 的职责；JSON 与 HTTP 的关系。
- 实践：阅读现有 main；先预测三种请求的行为，再自己增加 `GET /healthz` 与返回固定商品数组的 `GET /products`。先写成功响应和字段约定。
- 算法：C++ 尝试 1「两数之和」，记录是否独立完成、复杂度与边界。
- 表达：用自己的话讲“请求从监听 socket 到 Handler 再到响应”的路径。
- 验收：保存三种预测及实际响应；新增接口可访问，商品列表的 Content-Type 和 JSON 结构符合自己的约定；能说明哪些请求进入了 Handler。

开始前预测：`GET /`、`GET /missing`、`POST /` 是否都会执行 root Handler？分别可能得到什么结果？先写理由，再运行观察。

## Day 2：商品模型与详情查询（W01-D2）

- 理论（A）：Serialize/Deserialize 的用途，`Path` 提取与 `IntoResponse`。
- 实践：定义商品字段与类型，使用固定初始数据实现 `GET /products/:id`；区分不存在与 ID 解析失败。只有需要接收请求体时才引入对应输入类型。
- 算法：49「字母异位词分组」，写清哈希键设计与复杂度。
- 表达：404 与 400 的差别；参数提取失败发生在哪一层？
- 验收：已有商品、合法但不存在的 ID、非数字 ID 三条请求有证据，返回码符合接口约定；金额不用浮点数表示。

事前预测：`/products/abc` 会进入你写的查询函数吗？用日志或断点验证。

## Day 3：共享状态与创建（W01-D3）

- 理论（A/T）：AppState、Arc、Mutex、guard 与锁作用域；避免持锁跨 await。
- 实践：把集合变为应用共享状态，实现 `POST /products`；由服务端生成 ID，校验空白名称、金额、库存与字段上限。ID 分配不能只用当前集合长度猜测。
- 算法：283「移动零」，解释原地处理与复杂度；按算法机制复做到期题。
- 表达：Arc 的 clone 是否会复制整个集合？为什么需要互斥？
- 验收：一次请求创建的数据可被另一次请求读到；非法输入不会改变状态；说清返回对象与 guard 的生命周期。

事前预测：如果每次请求都创建新集合，会发生什么？如果删除一个商品后再创建，用集合长度分配 ID 会有什么问题？

## Day 4：更新、删除与错误约定（W01-D4）

- 理论（H/A）：PUT 的预期语义、状态码、Result 与 IntoResponse。
- 实践：实现完整更新和删除；建立最小业务错误分类，使自己的错误响应格式一致。明确框架提取器拒绝是否也已统一，尚未统一的记录为缺口。
- 算法：11「盛最多水的容器」，解释双指针移动依据。
- 表达：为什么重复 DELETE 的状态码不同也可能符合幂等语义？
- 验收：创建→查询→更新→查询→删除→再查形成完整序列；不存在与非法输入可区分；更新不擅自改变商品 ID。

事前预测：删除同一个 ID 两次，第二次集合状态会怎样？实现前先确定接口约定，再观察。

## 起始接口与数据约定

| 接口 | 本周契约 |
|---|---|
| `GET /healthz` | 200，简单存活响应 |
| `GET /products` | 200，JSON 数组，空集合返回 `[]` |
| `GET /products/:id` | 存在 200，不存在 404，非法 ID 400 |
| `POST /products` | 成功 201，服务端分配 ID；输入校验失败不得改变集合 |
| `PUT /products/:id` | 完整更新成功 200，不存在 404；ID 不可被请求体修改 |
| `DELETE /products/:id` | 成功 204 且无响应 body，再次删除按约定返回 404 |

数据最小字段：id、name、price_cents、stock。自行选择整数类型、上限与空白名称规则并写入 API 说明。输入/输出 DTO 可以分开；验证字段与数值转换时要覆盖溢出或超范围。

业务输入错误暂定 400；非法 JSON、缺字段、错误 Content-Type 等框架拒绝可能有不同默认行为，需先观察并记录，再决定如何统一，不能只改 README 宣称已统一。错误 body 使用稳定的 code/message，暂不要求复杂错误框架。

| 正常路径 | 列表/详情、创建后查询、更新后查询、删除后查询 | 接口状态和集合内容一致 |
