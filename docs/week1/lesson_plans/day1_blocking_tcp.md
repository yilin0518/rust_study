# Day 1 教学教案：阻塞式 TCP Echo Server

## 教学目标

学习者能够独立实现并解释单线程、单连接的阻塞式 Echo Server，并以运行结果说明 `read()`、`read() == 0`、缓冲区切片和 TCP 字节流。

## 先备状态

- 已理解 `TcpListener::bind`、`accept()` 的作用和阻塞行为。
- 起始程序可接受一个 TCP 连接。

## 教学顺序

1. 让学习者完成一次 `read()`，并预测返回值 `n` 的含义。
2. 通过短消息实验确认只能使用 `&buffer[..n]`。
3. 引入 `Write::write_all`，让学习者实现一次回显；Windows 使用 PowerShell 的 `TcpClient` 验证。
4. 讨论数据进入服务端内核发送缓冲区、客户端内核接收缓冲区及正常关闭的顺序。
5. 让学习者预测客户端断开后的第二次 `read()`；观察 `Ok(0)`。
6. 将读取改为内层循环，要求主动处理零字节读取，避免空转。
7. 将 `accept()` 改为外层循环，验证多个客户端可依次服务。
8. 让两个客户端同时保持连接，观察服务端阻塞在第一个连接的 `read()`；明确 Day 2 的动机。

## 必须提问的预测点

- `n` 为什么不能忽略？
- 客户端已连接但未发送数据时，`read()` 如何表现？
- 客户端关闭后，下一次 `read()` 返回什么？
- 为什么 `Ok(0)` 若不退出循环会导致空转？
- 单线程的外层 `accept()` 循环能否同时处理两个连接？

## 常见误区与纠正

- 不要把 TCP 当成消息协议；一次 `read()` 不保证对应一次发送。
- `write_all` 返回不表示客户端程序已经显示数据；数据先由服务端内核接管。
- `Ok(0)` 是正常 EOF，不是读取错误。
- “可依次服务多个客户端”与“可同时服务多个客户端”不同。

## 完成证据

- 服务端回显任意一次读到的有效字节。
- 客户端关闭后服务端打印断开日志而不空转。
- 第一个客户端保持空闲时，第二个客户端无法得到服务端处理。
