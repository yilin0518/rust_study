# Day 2 教学教案：一连接一线程

## 教学目标

学习者能够将 Day 1 的连接处理循环移到独立 OS 线程中，使多个客户端能够并发获得 Echo；并能够解释 `move`、所有权转移、`Send` 和 `'static` 约束，以及这种模型的可扩展性限制。

## 先备状态

- 已完成 Day 1 的外层 `accept` 和内层 Echo 循环。
- 能说明单线程为何卡在某个连接的阻塞 `read()` 上。

## 教学顺序

1. 复述 Day 1 的阻塞点与多客户端限制。
2. 将单连接处理逻辑提取为 `handle_connection(stream, addr)` 的函数；先不创建线程。
3. 让学习者尝试在 `thread::spawn` 闭包中借用 `stream`，阅读编译错误。
4. 询问线程可能比当前函数活得更久时，借用为何不安全。
5. 引入 `move`，将 `TcpStream` 的所有权转交给闭包；明确原作用域不能再使用它。
6. 解释 `TcpStream` 可跨线程移动需要 `Send`，并指出线程入口通常要求捕获值不借用当前栈帧（`'static`）。
7. 用两个保持连接的 PowerShell 客户端并发发送，验证各自获得回显。
8. 通过讨论或有限实验指出线程数量、栈、上下文切换与阻塞资源的成本；不提前优化。

## 提示升级

1. 概念提示：一个连接的阻塞读取不应占住接受新连接的线程。
2. API 提示：查看 `std::thread::spawn` 和闭包的 `move` 关键字。
3. 结构提示：主线程只做 accept；新线程调用连接处理函数。
4. 局部代码：仅在学习者尝试后解释某一个所有权或生命周期错误。

## 必须提问的预测点

- 不写 `move` 时，编译器在防止什么？
- `move` 后，主线程还能使用 `stream` 吗？
- 两条连接是否各自拥有独立的 `TcpStream`？
- 线程模型解决了什么，又没有解决什么？

## 完成证据

- 两个已连接的客户端都能在对方保持空闲时获得 Echo。
- 学习者能解释 `move` 是所有权转移，而不是数据深拷贝。
- 学习者能说明一连接一线程在大量连接下的资源成本。
