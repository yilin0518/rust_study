# 3～6 个月后端实习准备路线

## 1. 求职定位

主要目标是中国大陆互联网公司的通用后端开发实习，而不是限定为 Rust 岗位。学习顺序调整为先集中完成 Rust 网络与 Redis Clone，再转入 Go 后端：

```text
Rust：当前主线，网络、并发、协议和系统能力
Go：Rust 阶段完成后的主要就业语言和生产后端项目
SQL / Linux / 计算机基础：共同底座
```

Rust 和 Go 都适合网络与并发程序，但不能无成本互换。可以迁移的是网络、并发、错误处理、测试和性能分析等思想；Go 的 interface、goroutine、channel、context、GC 和后端生态需要单独学习。

时间目标随之调整：

- 第 1～2 周完成阻塞、线程、Future 和最小 Tokio 的前置链路。
- 第 3～10 周完成 Redis Clone 核心与高级章节，并做独立扩展和工程验收。
- 第 11 周开始 Go；第 16～18 周形成第一个可投递的 Go 后端项目版本。
- 第 24 周形成一个成熟 Go 业务项目和一个成熟 Rust 网络系统项目。

这意味着不再以“第 8 周拥有 Go 项目”为目标。若严格完成整个 Redis Clone 后才学习 Go，普通 Go 后端岗位的有效投递时间更接近第 4～5 个月。

AI Infra 暂不进入前 6 个月主线。数据库、缓存、消息、可靠性、服务治理和性能分析掌握之后，再决定是否转向 AI Infra。

## 2. 什么叫成熟项目

项目不能只证明“使用过框架”。进入简历前至少满足：

- 有真实使用者、业务目标和明确边界。
- 有需求文档、API 契约、数据模型、状态机或核心不变量。
- 有认证授权、参数校验、错误模型、配置和日志。
- 有数据库 migration、单元测试、集成测试和关键端到端测试。
- 能通过 Docker Compose 在新环境启动。
- 有指标和 Trace，能够定位失败与性能问题。
- 有超时、取消、重试、幂等、并发、一致性或降级等真实机制。
- 有故障注入、压测方法、原始数据和瓶颈分析。
- README 说明架构、运行方法、设计取舍、容量边界和未保证事项。
- 学习者能够独立解释和修改关键实现。

“几十万吞吐”不是预先承诺。性能必须写成可复现实验：硬件、数据大小、连接数、读写比例、持续时间、p50/p95/p99、错误率和资源占用都必须公开。没有达到某个数字时，也应通过证据说明瓶颈并完成一次有效优化。

## 3. 三个互补项目

### 项目 A：团队协作与工单系统（Go，业务后端主项目）

#### 使用场景

面向小型研发团队管理项目、成员、工单和评论。它不是纯 CRUD：工单具有负责人、优先级、标签、状态流转、截止时间、订阅和操作历史；不同组织的数据必须隔离。

#### 技术栈

```text
Go + net/http/chi（先理解标准库，再选择轻量路由）
PostgreSQL + pgx/sqlc
Redis
JWT 或服务端 Session
OpenAPI
Prometheus + OpenTelemetry
Docker Compose + GitHub Actions
```

#### 核心领域

```text
Organization / User / Membership / Role
Project / Issue / Comment / Label
IssueStatusTransition / AuditLog / Notification
```

#### 必须解决的问题

- 多租户数据隔离：用户不能通过猜 ID 访问其他组织数据。
- RBAC：Owner、Maintainer、Member 的操作范围不同。
- 状态机：非法工单状态迁移必须被拒绝。
- 并发更新：两人同时编辑时不能静默覆盖。
- 事务：状态变更、审计记录和事件写入必须保持一致。
- 使用游标分页，避免深分页退化。
- 说明缓存对象、失效方式和不一致窗口。
- 数据库提交成功后可靠地产生通知事件。
- 限流、超时、优雅关闭和统一错误响应。

#### 分阶段实现

- V1：组织、成员、项目、工单、评论、RBAC、PostgreSQL、migration、测试。
- V2：乐观并发控制、审计日志、游标分页、搜索、Redis 缓存、OpenAPI、Docker Compose。
- V3：使用 Transactional Outbox 产生通知事件，加入消费者、重试、幂等、指标、Trace 和故障实验。

#### 项目验收

- 权限矩阵和状态迁移均有自动化测试。
- 能演示事务回滚、并发更新冲突、缓存失效和消费者重复处理。
- 有典型查询的 `EXPLAIN ANALYZE` 及索引前后对比。
- 新环境可以一条命令启动并执行端到端测试。

### 项目 B：可靠事件与通知平台（Go，异步与分布式后端项目）

#### 使用场景

项目 A 或其他服务产生事件后，平台根据订阅将通知投递到 Webhook、邮件模拟器或站内信。下游可能超时、返回 500、永久失败或重复收到消息。

```text
Producer -> Event API -> durable storage / broker -> Workers -> Endpoints
```

#### 技术栈

```text
Go
Kafka（主版本）或 RabbitMQ（若更关注工作队列语义）
PostgreSQL
Redis（限流与短期状态）
HMAC-SHA256
Prometheus + Grafana + OpenTelemetry
k6 / Vegeta
Docker Compose
```

消息中间件不是一开始就加入。先用 PostgreSQL Outbox/队列表实现正确性，观察吞吐或解耦限制后再引入 Kafka，并比较两版语义和性能。

#### 必须解决的问题

- 生产者重试时避免重复创建事件。
- 数据库业务提交与事件发布之间避免丢消息。
- 至少一次投递为什么产生重复，消费者如何幂等。
- HTTP 2xx、4xx、5xx、超时分别如何处理。
- 指数退避和 jitter 如何避免重试风暴。
- 失败达到上限后进入 DLQ、检查和 Replay。
- 每租户和每 Endpoint 限流及故障隔离。
- HMAC 签名和防重放。
- 队列积压时的背压和恢复时间估算。
- Worker 崩溃和部署过程中避免静默丢失事件。

#### 性能目标

不预设虚假的“几十万端到端 Webhook/s”，而是分层测量：

- 接收 API 的持久化吞吐和延迟。
- Broker 生产/消费吞吐。
- 调度器在内存 Mock Endpoint 下的吞吐。
- 真实 HTTP Endpoint 下的成功率、尾延迟和连接池表现。
- 10%、30%、50% 临时失败率下的积压和恢复时间。

若在注明硬件与 Mock 条件下达到十万级事件/秒，可以如实写入简历；否则以完整实验和优化结果替代数字宣传。

#### 项目验收

- 证明一次数据库提交后，事件不会因进程崩溃而永久丢失。
- 故障注入后最终成功或进入 DLQ，状态可审计。
- 重复消息不会产生重复业务副作用。
- 提供性能报告、容量模型和至少一次优化前后对比。

### 项目 C：高性能限流与 API Gateway 数据面（Rust，系统项目）

#### 使用场景

为项目 A/B 或独立上游服务提供反向代理、请求限流、超时、熔断、健康检查和指标。控制面只负责下发配置，Rust 数据面负责低延迟请求转发。

当前 TCP 学习演进为该项目基础：

```text
阻塞 TCP
 -> 一连接一线程
 -> Future / Tokio
 -> HTTP 代理
 -> 限流与超时
 -> 上游连接池与负载均衡
 -> 熔断和动态配置
 -> 压测与性能分析
```

#### 技术栈

```text
Rust + Tokio + Hyper/Axum
Tower middleware
Redis（可选分布式限流）
Prometheus + tracing
wrk / k6 / 自定义负载工具
Docker Compose
```

#### 必须解决的问题

- Token Bucket 或 GCRA 的时间和并发正确性。
- 本地限流与分布式限流的一致性/性能取舍。
- 请求体大小限制、超时传播和客户端取消。
- 上游连接池、健康检查和负载均衡。
- 哪些失败可以重试，为什么非幂等请求不能盲目重试。
- 熔断器 Closed/Open/Half-Open 状态转换。
- 配置更新原子生效且不影响在途请求。
- 慢上游和大量连接下的背压。

#### V1 范围

- 固定路由反向代理。
- 请求 ID、结构化日志和指标。
- 本地 Token Bucket。
- 超时与优雅关闭。
- 两种简单负载均衡。
- 健康检查和基础熔断。

暂不复刻完整 Kong/Envoy，后续再考虑 Redis 限流、热更新和多协议。

#### 性能目标

分别测量直连上游、纯代理、代理+日志、代理+限流、代理+指标的开销，报告吞吐、p50/p95/p99、错误率、CPU 和内存。十万级吞吐只在硬件、连接模型、payload 和测试命令可复现时才写入简历。

## 4. 三个项目的能力覆盖

| HTTP API 与权限 | 强 | 中 | 中 |
| PostgreSQL 与事务 | 强 | 强 | 弱 |

## 5. 第 1～10 周：Rust 网络与 Redis Clone

### 第 1～2 周：完成前置网络链路

- 完成当前 handler 提取和 thread-per-connection。
- 通过编译错误理解闭包捕获、`move`、`Send` 和 `'static`。
- 使用多个保持连接的客户端验证并发行为。
- 完成一个最小 Future 实验，理解 `Poll::Pending`、Waker 和 executor。
- 实现最小 Tokio Echo，对比线程与 task。

### 第 3～6 周：Redis Clone 核心

- 按教程完成 Initial Steps、RESP、GET/SET、Key Expiry。
- 每一步先读需求和测试，自己实现后再查看作者方案。
- 为 RESP 增加半包、一次多帧、非法长度、超大帧和断连测试。
- 使用真实 `redis-cli` 做兼容性验证。
- 记录协议解析中的所有权、分配和错误模型。

### 第 7～8 周：并发与工程生命周期

- 完成 Actor 并发和命令重构章节。
- 比较 Actor 与 `Arc<RwLock<...>>` 的正确性、复杂度和争用。
- 加入连接上限、空闲超时、背压、结构化日志和优雅关闭。
- 运行并解释并发测试，排查任务泄漏或无界队列风险。

### 第 9～10 周：复制、事务与独立验收

- 完成教程的复制和事务章节；对尚未完成或有疑问的内容以 Redis 官方语义为准。
- 不把“教程代码通过”作为完成标准。
- 增加至少一个教程外的故障实验和一个性能实验。
- 形成协议说明、架构图、测试说明、Benchmark 方法、结果和已知限制。
- 能独立解释一次完整请求从 socket 到 RESP、命令执行和响应的路径。

如果第 10 周仍不能独立解释核心路径，应补足理解；如果只是高级兼容细节尚未完成，则记录为后续事项，不无限推迟 Go。

## 6. 第 11～22 周：Go 基础与项目 A

### 第 11～12 周：Go 基础

Go：package、函数、struct、method、interface、slice/map、pointer、多返回值、error、`defer`、module、`go test`、格式化与静态检查。

小实验服务于项目 A 的领域模型，不成为独立简历项目。

### 第 13～14 周：Go HTTP、并发和测试

- `net/http`、JSON、middleware、状态码和 REST 契约。
- goroutine、channel、mutex、WaitGroup、race detector。
- `context.Context`、取消、deadline 和请求生命周期。
- 使用内存 Repository 完成项目 A 的组织、项目和工单核心模型。
- 编写 handler、service 和 domain 单元测试。

### 第 15～16 周：PostgreSQL 与事务

- SQL、约束、JOIN、索引、事务、隔离级别和 `EXPLAIN ANALYZE`。
- pgx/sqlc、连接池、migration 和数据库集成测试。
- 项目 A 完成多租户、RBAC、状态机和审计记录。
- 通过唯一约束和事务保证关键不变量。

### 第 17～18 周：工程化与第一次集中投递

- 认证、统一错误模型、配置、结构化日志、优雅关闭。
- 游标分页、乐观并发控制和必要索引。
- Docker Compose、OpenAPI、CI 和端到端测试。
- 完成第一版架构说明和简历，开始小规模投递。

### 第 19～20 周：缓存与异步事件

- 先明确瓶颈和一致性要求，再为项目 A 引入 Redis。
- 学习 Cache Aside、失效策略和缓存穿透/击穿。
- 实现 Transactional Outbox 和通知消费者。
- 测试重复消费、消费者崩溃和数据库回滚。

### 第 21～22 周：可观测性、故障和交付

- Prometheus 指标、OpenTelemetry Trace 和请求/事件关联 ID。
- 数据库慢查询、缓存故障、消费者失败和过载实验。
- 压测一个读路径和一个写路径，完成性能报告。
- 项目 A 达到成熟的可投递状态；Rust 项目保留为第二个核心简历项目。

## 7. 第 23 周以后：项目 B 和项目 C

### 第 23～26 周：可靠事件平台正确性版本

- 基于 PostgreSQL 实现事件、投递、尝试记录、重试和 DLQ。
- 实现幂等键、HMAC、防重放和 Endpoint 隔离。
- 构建可控制成功、超时、慢响应和失败概率的测试 Endpoint。
- 完成崩溃恢复和 Replay 测试。

### 第 27～30 周：消息中间件和性能版本

- 学习 Kafka 的 partition、consumer group、offset 和投递语义。
- 将 Kafka 引入项目 B，并与数据库队列版比较。
- 实现背压、租户限流、指标和 Trace。
- 完成分层压测、容量模型和故障报告。
- 项目 B 达到可投递状态。

### 后续：Rust Gateway 可验证版本

- 从已完成的 Tokio 网络基础进入 HTTP 代理。
- 实现本地限流、超时、健康检查、负载均衡和熔断。
- 为限流算法、状态机和失败路径编写测试。
- 对各中间件开关进行分层 benchmark。
- 若 A/B 尚未成熟，优先修复它们，不为了数量留下第三个半成品。

## 8. 持续学习线

每周建议：

```text
45% 项目设计、实现与测试
20% Go / Rust / 后端知识
15% 数据结构与算法
10% 网络、操作系统、数据库基础
10% JD、简历、投递和复盘
```

面试知识与项目同步：

- 网络：TCP、HTTP、连接复用、超时、DNS、代理。
- 操作系统：进程线程、调度、内存、文件描述符、I/O。
- 数据库：索引、事务、隔离级别、锁、慢查询。
- 并发：竞态、锁、channel、context、背压。
- 后端：缓存、消息、幂等、限流、熔断、降级、可观测性。
- 算法：保持稳定练习，不占用项目主体时间。

## 9. 学习方式

```text
提出真实问题
 -> 预测行为
 -> 最小实验
 -> 观察并解释
 -> 设计接口和不变量
 -> 集成到项目
 -> 测试失败路径
 -> 压测或故障验证
 -> 记录取舍
```

Codex 不直接生成整个项目。学习者先设计或实现一个小增量，Codex 负责审查正确性、Go/Rust 语义、系统行为和工程质量，并按提示等级逐步提供帮助。
